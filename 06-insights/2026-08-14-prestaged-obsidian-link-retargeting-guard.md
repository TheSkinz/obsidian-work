## The Question

Given a confirmed second instance of the same ambiguous-bare-link pattern still sitting live in the vault (this run's own finding, not yet fixed by anyone), and no existing lint rule or hook that would catch a wikilink resolving to the *wrong* target rather than resolving to nothing: should the vault add a mechanical `LINK-FACILITY`-style lint check, treat this as a one-time remediation with no new tooling, or fold the question into DQ-003 (still open) rather than deciding it separately?

## Proposed Change

### A. Add a `LINK-FACILITY` lint rule

For any wikilink whose target path runs through a facility folder (`02-facilities/<Company>/<Site>/...`), flag it when the target's facility segment doesn't match either the linking note's own `facility:` frontmatter (if present) or the linking note's own containing folder. Would have caught the 2026-07-30 mis-resolution mechanically and, per this run's finding, would also flag the still-live bad link in `archive/2026-06-26-cnd25004-candidate-canonical-updates.md:12` today. Needs an explicit exclusion for generated index files (`INDEX.md`) to avoid misfiring on its by-design bare links.

## Risks and Counter-Arguments

Option A adds a fourteenth lint rule to a system Jesse has previously pushed back toward propose-only, low-ceremony (2026-07-03 policing-pattern rejection) — though DQ-003's own WORD-DELTA extension was accepted on the grounds that a narrow, mechanically-scoped data-integrity check is a different shape than open-ended policing, and A here is comparably narrow (one path-segment comparison, not general content review). Option B leaves the gap open for any future bulk-link operation (a vault reorganization, a facility rename, a future Obsidian plugin) to repeat the same failure silently, since DEAD-LINK still would not catch it — the "Source mode should prevent recurrence" argument is unverified, since Source mode was already enabled *before* B-101's original 2026-07-19 incident type existed, but this link-expansion event is a different Obsidian feature (wikilink autocomplete/expansion, not the Live Preview table editor) and may not be gated by the same setting at all. Option C risks the narrower, still-live finding (the archive file's uncorrected frontmatter link) getting lost inside DQ-003's broader and differently-framed question, which is about content *loss*, not link *correctness* — the two failure modes don't share a detection mechanism.
