# Grok Bot power-user research (2026-10)

Read-only web research, about twenty minutes, run 2026-10-04. Coverage is thinner than for Cursor or Claude Code but not empty: xAI's own docs at `docs.x.ai/grok-bot/` and Cursor's help pages are the primary sources, the Cursor community forum is where staff actually answer questions, and a layer of third-party blogs restates both. X long-form articles (the "Memory Map" and "Masterclass" pieces) returned HTTP 402 to the fetcher, so only their search-result snippets were read. No Reddit thread was opened directly; Reddit claims below come second-hand through a cellcog.ai roundup and are marked that way. Product launch date per xAI's announcement coverage is 2026-08-11, not September.

Every claim is tagged **[source states]** (a page says it outright) or **[inferred]** (my conclusion). The cost/benefit line on each finding assumes Jesse's setup: about 15 Bots doing field-service paperwork on a weekly usage allowance, with a Python toolchain already proven on Linda2.

## 1. Memory beyond the single thread

**The thread is the cost problem, not just a memory problem.** [source states] Cursor staff on the forum: "the full transcript gets sent to the model on every turn, and there aren't any explicit controls yet to drop older messages" ([forum 168333](https://forum.cursor.com/t/grok-bot-prune-compact-an-agent-s-context-without-creating-a-new-bot/168333)). Auto-summarization near the context limit exists but staff say it is not the same as a compact or a new session. A Sept 14 staff reply says each usage row is roughly the conversation size, mostly cached tokens, and one user logged 10.1K growing to 254.6K tokens over seven turns ([forum 171540](https://forum.cursor.com/t/grok-bot-context-window-size-and-token-accumulation-logic-in-pro/171540)). Cost/benefit: this is the single biggest usage lever for 15 Bots; every long-lived Bot taxes every future turn.

**Staff-endorsed reset: duplicate the Bot.** [source states] Cursor staff (Mohit Jain) recommend asking the Bot for a handoff summary, right-click > Duplicate (keeps name, instructions, avatar), paste the summary into the copy, hide the original; one tester measured about 75% token reduction. Caveat from a Sept 22 post: "Memory does not carry over," so the copy must be re-taught ([forum 171540](https://forum.cursor.com/t/grok-bot-context-window-size-and-token-accumulation-logic-in-pro/171540)). Sequence: `Ask Bot for handoff summary > right-click Bot > Duplicate > paste summary > hide original`. Cost/benefit: cheap to do and large saving, but it only works if durable facts already live in files rather than in learned memory.

**Group-chat-as-new-session workaround.** [source states] Users on forum 168333 create a new group chat containing the same Bot so the old 1:1 transcript is not reloaded ([forum 168333](https://forum.cursor.com/t/grok-bot-prune-compact-an-agent-s-context-without-creating-a-new-bot/168333)). [inferred] Groups pull in other Bots' identity and skill catalogs (forum 171540 lists this as an accumulator), so a single-Bot group is probably cleaner than a multi-Bot one. Cost/benefit: zero setup and keeps learned memory, which beats duplication for Bots that have accumulated useful memory; unverified how long the group thread itself stays cheap.

**Files in /workspace are the community's memory layer.** [source states] The xAI docs say a Bot "can retain stable working preferences, important facts, and summaries" but "Memory is not a substitute for an authoritative source" ([docs: Bots](https://docs.x.ai/grok-bot/bots)). Vellum's review says individual memories cannot be inspected, corrected, exported or deleted ([Vellum](https://www.vellum.ai/blog/official-grok-bot-breakdown)). The DataCamp tutorial's pattern is a `/workspace/learner-profile.md` the Bot reopens before every run ([DataCamp](https://www.datacamp.com/tutorial/grok-bot-tutorial)). The most-cited team convention (attributed to Akshay Pachaar) is a board file, one file per task, and a handoffs folder, with exactly one Bot allowed to write the board, because concurrent writes lose an edit silently; messages carry file paths, not content ([aibuilderclub](https://www.aibuilderclub.com/blog/grok-bot-guide)). The "Memory Map" X article names seven homes: Bot description, conversation, learned memory, skill, routine, /workspace, and the original source system (search snippet only; [X article](https://x.com/i/article/2096550148201435621)). Cost/benefit: the existing `state.md` one-thread pattern from the 2026-10-04 commits already matches this; the addition worth making is the single-writer rule per shared file.

**Skills as memory.** [source states] Private skills are "one library shared by all your Bots" ([docs: skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)); a skill is a folder with a `SKILL.md` (YAML `name`/`description` plus a Markdown body) per the community catalogues ([jaskirat1616/grok-skills](https://github.com/jaskirat1616/grok-skills), [coolxeo/grok-bot-skills](https://github.com/coolxeo/grok-bot-skills)). [source states] coolxeo notes installation into Grok Bot through its CLI "has not been verified"; nobody documents the on-disk skills path. [inferred] Skills hold method, not facts, so they reduce what a thread must carry but do not replace a facts file. Cost/benefit: a receipt-extraction skill loaded only when invoked is cheaper than restating the method in each Bot's description.

**Profile description for rules that stay true.** [source states] Docs: "Use the description for rules that should remain true," task specifics go in messages ([docs: Bots](https://docs.x.ai/grok-bot/bots)). Cost/benefit: neutral; keep descriptions short since they ride on every turn [inferred].

## 2. Persistence of installs

**Only /workspace, files, browser state and logins persist; apt and system installs do not.** [source states] xAI docs: "Treat temporary directories, manually installed packages, and uncommitted application state as replaceable" ([docs: computer and apps](https://docs.x.ai/grok-bot/computer-and-apps)). Cursor's recovery page says a computer update keeps Bots, files and logins and removes "installed apps and packages"; Recover and Reset remove them too, and project folders like `node_modules` and Python venvs are not preserved ([Cursor help: computer recovery](https://cursor.com/help/grok-bot/computer-recovery)). Staff on the forum: anything installed "via apt or into system folders" won't survive a rebuild, and rebuilds also happen during automatic version rollouts, not only when you press Update ([forum 169847](https://forum.cursor.com/t/cloud-computer-wipes-packages-after-rebuild/169847)). A separate bug report says Chrome extensions also vanish after a computer update ([forum 168385](https://forum.cursor.com/t/grok-bot-chrome-extensions-disappear-after-a-computer-update/168385), title only). The computer hibernates when idle and background processes die ([grokbot.run](https://grokbot.run/learn/computer/), citing xAI troubleshooting).

**Staff workaround is a package list file.** [source states] "keep a note file with the list of required packages, and after an update, ask the Bot to reinstall everything" ([forum 169847](https://forum.cursor.com/t/cloud-computer-wipes-packages-after-rebuild/169847)). Community refinement: put one line at the top of every skill that installs anything missing into `/workspace/bin`, copies configs from `/workspace/config`, and puts `/workspace/bin` on PATH; never apt-install into the system (search-result summary of a Grok Bot guide; source page not opened). The [woodegg/grok-bot-supercomputer](https://github.com/woodegg/grok-bot-supercomputer) repo goes further with Debian/Incus rootfs trees under /workspace and a five-minute scheduled `startup.sh` bootstrap (0 stars). Cost/benefit: a `/workspace/setup/bootstrap.sh` plus `packages.txt`, run idempotently at the top of each paperwork skill, costs a few seconds per run and prevents a whole fleet failing the morning after a silent rollout; the Incus approach is over-engineered for paperwork.

**Cursor's environment.json and snapshots do not apply.** [source states] Cursor cloud agents persist disk state through snapshots, `.cursor/environment.json` (`snapshot`, `install`, Dockerfile) built per repository ([Cursor docs: cloud environment setup](https://cursor.com/docs/cloud-agent/setup)). [inferred] Grok Bot exposes no repo binding or environment config, and its "Reset rebuilds from last saved snapshot" is a platform-managed snapshot, not a user-defined image; nothing found documents a user-controllable snapshot or install hook for Grok Bot. Cost/benefit: don't spend time looking for it.

[inferred] Pip packages installed with `pip install --target /workspace/pylib` or a venv under /workspace should survive updates as plain files, but Cursor's help page says Python venvs are "not preserved" — that line likely refers to venvs outside /workspace, unverified. Test it once before relying on it.

## 3. Cheaper, more reliable computer use

**Connector or script before browser.** [source states] xAI docs: "Prefer a supported connector when it exposes the action you need," browser only for services with no connector or a visual-only workflow ([learncursor summary of docs](https://www.learncursor.dev/learn/cursor-agents/grok-bot-computer-apps)); Flavio Copes's write-up: "Use the narrowest interface that can complete the job" ([flaviocopes](https://flaviocopes.com/grok-bot/)). The [grokbot-economy](https://github.com/wesleysimplicio/grokbot-economy) skill (0 stars) formalises a ladder of script/CLI, MCP, plugins/skills, APIs, a text/DOM `browse` CLI, then screenshot computer use last, with a `token_log.py` that logs path and tokens per task; it claims no measured savings. Cost/benefit: the ladder is the right default for receipts and forms; the logger is optional.

**Delegate heavy work to a terminal agent on its own allowance.** [source states] Aaron Makelky (2026-09-03, 2026-09-07 via ryandoser.com) runs Cursor Agent, Grok Build, Codex or Antigravity in the Bot's Linux terminal so execution draws on that agent's usage rather than Grok Bot's; he enforces the split with standing instructions on his top-level Bot ([Makelky](https://aaronmakelky.com/blog/how-to-get-more-grok-bot-usage), [ryandoser](https://ryandoser.com/is-grok-bot-worth-it/)). The workaround "stretches the limit rather than removing it." [inferred] Claude Code on the Bot's computer would work the same way, but CLI credentials are shared across all Bots, so any Bot could spend that subscription. Cost/benefit: large saving for document generation and batch PDF work; credential sharing is the trade.

**Tools worth installing.** Nothing found lists what the Grok Bot image ships with beyond browser, filesystem and terminal [source states, FAQ search summary], and nobody publishes a Grok Bot PDF/OCR toolchain. [inferred] The standard Linux set fits the paperwork: `poppler-utils` (`pdftotext`, `pdftoppm`), `ocrmypdf`/`tesseract` for scanned receipts, `pdftk` or Python `pypdf`/`PyMuPDF` for AcroForm fill, and `libreoffice --headless --convert-to pdf` for docx-to-PDF. All are apt installs, so they belong in the bootstrap list above, or as pip packages under /workspace. [inferred] The vault's own `tools/fill_service_receipt.py` already does the receipt PDF fill with PyMuPDF and could be copied to `/workspace/bin`. Cost/benefit: one scripted fill replaces dozens of screenshot steps per receipt, the biggest single computer-use saving available for this workload.

**Local execution on the desktop.** [source states] `Settings > General > Bot > Execution on Local Computer` with Ask every time / Always allow / Never allow; xAI recommends Never allow unless there's a specific need ([docs: security](https://docs.x.ai/grok-bot/security)). [inferred] This lets a Bot run Linda2's existing Python and vault tools instead of rebuilding them in the cloud, at the cost of Linda2 needing to be on and of a broad execution grant. Cost/benefit: worth it for one designated Bot on "Ask every time", not fleet-wide.

**Route traffic through this computer.** [source states] Members can "route traffic through their desktop to use its network and IP address" to reach private networks; hosted computers otherwise use shared static egress IPs ([docs: security](https://docs.x.ai/grok-bot/security)). [inferred] Useful only where a site blocks datacenter IPs or a resource is LAN-only. Cost/benefit: low relevance to receipts and email.

## 4. Bring-your-own MCP servers

**Custom MCP is supported, added by chat, not a config file.** [source states] Composio's guide: tell a Bot "Add a custom MCP server called [name] at [https URL]"; an approval card shows name, type, URL and headers, with an "Edit JSON" option, and saving registers it account-wide ([Composio](https://composio.dev/content/how-to-add-mcp-servers-to-grok-bot), [Scrapeless](https://www.scrapeless.com/en/blog/grok-bot-scrapeless-connector)). API keys go in a header on the server entry; OAuth servers raise a connect card and the token stays on the connector backend. Grok Bot has "no config file for MCP servers." Sources disagree on whether Settings > Plugins has a custom-server form (Omentir/Blotato snippets say yes; Composio and Scrapeless say chat only) — check the app. Cost/benefit: high value; one MCP for a PDF or forms service replaces browser steps for every Bot at once, since connectors are account-wide.

**Stdio servers run on the cloud computer.** [source states] "A command such as `npx -y some-mcp-server` does work, because the bot runs it on its own computer," with credentials stored as an environment variable on the entry ([Composio](https://composio.dev/content/how-to-add-mcp-servers-to-grok-bot)). Remote servers must be publicly reachable ([Vellum](https://www.vellum.ai/blog/official-grok-bot-breakdown)). [inferred] A stdio server installed under /workspace survives updates; one fetched by `npx` re-downloads after each rebuild, which is fine. A self-written stdio MCP wrapping the receipt-fill script is possible but the plain script via terminal is cheaper to build. Cost/benefit: medium; prefer scripts unless several Bots need a structured tool.

**Marketplace and aggregators.** [source states] Connectors install from `Settings > Plugins > Marketplace` and are account-wide; Grok Bot inherits the team's Cursor connector policy, and an MCP allowlist is Enterprise-only ([docs: computer and apps](https://docs.x.ai/grok-bot/computer-and-apps), [docs: teams](https://docs.x.ai/grok-bot/teams-and-enterprises), [docs: security](https://docs.x.ai/grok-bot/security)). Composio is in the Marketplace and fronts 1,000+ apps ([Composio guide](https://composio.dev/content/guide-to-frok-bot)). Event triggers for routines come from Cursor account integrations such as Slack and GitHub ([docs: skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)). Cost/benefit: Composio is the fastest path to an app with no native plugin, but each extra tool catalogue adds tokens to every turn [inferred], so install only what a Bot uses.

## Where nothing was found

No source documents where skills live on disk, a user-defined snapshot or install hook, the preinstalled package list, a memory viewer or editor for Grok Bot (the consumer Grok memory settings are a different product), or any measured comparison of screenshot versus CLI token cost. No Grok Bot user published a receipt, form or PDF workflow.

## Recommended next steps

The highest-return change is a fleet-wide context hygiene rule: durable facts in `/workspace` files with a single writer each, and a duplicate-or-new-group reset whenever a Bot's turns approach the 120K range. Second is a `/workspace/setup/bootstrap.sh` plus `packages.txt` (poppler, ocrmypdf, pdftk or PyMuPDF, LibreOffice) called at the top of each paperwork skill, with `fill_service_receipt.py` copied to `/workspace/bin`. Before relying on either, verify two things in the live app: whether pip installs under /workspace survive a computer update, and whether Settings > Plugins offers a custom MCP form or only the chat route.
