# Agent memory systems vs the existing vault (2026-10)

Read-only web research, about twenty minutes, run 2026-10-04, following [[research-2026-10-power-user]] and not repeating it. The question is whether the GitHub "second brain for agents" projects add anything to what the Grok Bot fleet already has: the read-only vault clone at `/workspace/vault` with `INDEX.md`, per-job `state.md` files with one writer each, the shared skill library, and `README-FOR-BOTS.md`. Every claim is tagged **[source states]** (a page says it outright) or **[inferred]** (my conclusion). Repo READMEs were read through a fetch-and-summarize tool, so short quotes are as the tool returned them.

The blunt answer is that almost none of them add value here. Jesse already runs the most-cited pattern in this space (Karpathy's LLM wiki) in a stricter, governed form. The heavyweight systems (mem0, Zep/Graphiti, Letta) solve a different problem — extracting facts from chat logs for consumer or support bots — and each would bring an API key, a database, and an opaque fact store that reproduces exactly the weakness of Grok Bot's own learned memory. The real gap in the fleet is not a memory system; it is that each Bot's private working knowledge lives in an uninspectable learned memory that dies on Duplicate. That gap is closed with one plain file per Bot, not a repo.

## Two platform facts that decide everything below

**Stdio MCP runs on the Bot's cloud computer, and the staff "no stdio" answer is about your own PC.** [source states] Composio: "A command such as `npx -y some-mcp-server` does work, because the bot runs it on its own computer," and the process "is also available to your other agents on that computer" ([Composio](https://composio.dev/content/how-to-add-mcp-servers-to-grok-bot)). [source states] Cursor staff (Kevin Neilson, 2026-08-13): "Grok Bot does not attach MCP servers that run on your own machine, whether that's stdio or something listening on localhost" ([forum 168182](https://forum.cursor.com/t/does-grok-bot-support-local-mcp-e-g-workflowy/168182)). [inferred] These do not conflict: the staff line is about Linda2, not the cloud box. Composio does not say whether a stdio server survives a computer update; per the prior note, anything installed outside `/workspace` will not.

**An account-wide MCP is a per-turn tax on every Bot.** [source states] Tool definitions "sit in the prompt at full size on the first turn and every turn after, regardless of whether the agent calls anything," at roughly 200 to 500 tokens per tool ([decagon](https://decagon.ai/glossary/what-is-mcp-context-bloat), [MCP spec issue 2808](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/2808)). [inferred] Because Grok Bot connectors register account-wide, a 15-tool memory server costs something like 3K to 7K tokens on every turn of every one of 15 Bots, and since the whole transcript is resent each turn that cost compounds with thread length. The same capability exposed as a terminal command costs nothing until called. This is the main reason the ranking below prefers CLIs and files over MCP servers.

## The systems, one by one

**Karpathy LLM wiki (pattern, not software).** [source states] Three layers: immutable raw sources, an LLM-maintained wiki of markdown pages, and a schema file; three operations: ingest, query, and lint for "contradictions between pages, stale claims," and orphans; an `index.md` that is "a catalog of everything in the wiki—each page listed with a link, a one-line summary," plus an append-only `log.md`; and "at small scale the index file is enough, but as the wiki grows you want proper search" ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). Runs on Grok Bot: yes, it is plain files. [inferred] What it adds: nothing. The vault is this pattern already — `INDEX.md` is the index, `change-log.md` is the log, `vault_lint.py` and `health.md` are the lint pass, CLAUDE.md and the canonical heater card are the schema — and it is stricter than Karpathy's version, because Karpathy lets the LLM own the wiki layer outright while Jesse's Lane 4 rule withholds domain-truth edits. Cost: zero. Verdict: already adopted; the gist is a useful thing to show someone asking what the vault is.

**basic-memory (basicmachines-co).** [source states] A stdio MCP server, installed by `uv tool install basic-memory` or run with `uvx basic-memory mcp`, that writes Markdown to `~/basic-memory`, indexes it in SQLite, keeps config at `~/.basic-memory/config.json`, and exposes about fifteen tools (`write_note`, `read_note`, `edit_note`, `move_note`, `delete_note`, `search_notes`, `build_context`, project and schema tools); semantic search uses a locally downloaded FastEmbed model; licence AGPL-3.0 ([GitHub](https://github.com/basicmachines-co/basic-memory)). Runs on Grok Bot: yes as stdio, but [inferred] `uv`, the FastEmbed model cache and `~/.basic-memory` all sit outside `/workspace` and would be wiped on update unless relocated by config and a bootstrap reinstall. [inferred] What it adds: a write path into a markdown knowledge graph — which is exactly what the Bots must not have against the vault, and pointing it at a separate `/workspace/memory` folder would create a second, ungoverned knowledge store competing with the vault. Cost: roughly 15 tool schemas on every turn of every Bot, plus a fragile install. Verdict: skip.

**mem0 / OpenMemory.** [source states] Each `add()` makes an LLM call that extracts memories; the April 2026 algorithm is "Single-pass ADD-only extraction — one LLM call, no UPDATE/DELETE. Memories accumulate; nothing is overwritten"; defaults are OpenAI `gpt-5-mini` and `text-embedding-3-small`, so an OpenAI key is required; self-hosting runs on Docker Compose with Qdrant; it reports 92.5 on LoCoMo and 94.4 on LongMemEval; Apache 2.0 ([GitHub](https://github.com/mem0ai/mem0)). Runs on Grok Bot: only as the hosted platform via remote MCP [inferred — Docker on the Bot's computer is not documented and would not persist outside `/workspace`]. [inferred] What it adds: automatic fact extraction from conversation, which is the same opaque, uninspectable memory Vellum already criticised in Grok Bot itself, now in a third-party cloud with its own API bill, and the ADD-only design means a superseded pig size or rate stays retrievable alongside the new one. The benchmarks measure recall of chat facts, not whether a heater-card value is right. Cost: OpenAI key, per-write LLM calls, hosted account. Verdict: skip.

**Letta (formerly MemGPT).** [source states] Letta is "a platform for stateful agents," shipping "the agent harness, interactive terminal UI, App Server, channels, and the runtime," with active work in `letta-ai/letta-code` ([GitHub](https://github.com/letta-ai/letta)). [inferred] It is an agent runtime, not a memory plugin — adopting it means running agents in Letta instead of Grok Bot. The one idea worth borrowing is MemGPT's memory blocks (small, always-in-context, self-edited notes), and the per-Bot memory file recommended below is that idea in a plain file. Cost: a second agent platform. Verdict: skip the software, take the idea.

**Zep / Graphiti.** [source states] Graphiti builds "temporal context graphs" where "Facts have validity windows. When information changes, old facts are invalidated — not deleted"; it needs Neo4j, FalkorDB or Neptune plus an LLM key, and warns that providers without structured output, "particularly... smaller models," cause ingestion failures ([GitHub](https://github.com/getzep/graphiti)). Zep Community Edition is deprecated and Zep Cloud's paid tier starts at $1,250 per year ([atlan](https://atlan.com/know/zep-vs-mem0/), [vectorize](https://vectorize.io/articles/zep-alternatives)). Runs on Grok Bot: not practically — a graph database on a computer that drops installed packages [inferred]. [inferred] What it adds: bi-temporal facts are a genuinely good model for "what did we charge at Baytown then vs now," but the vault already answers that with dated quote notes, `rate_history_rollup.py` and git history. Cost: database, LLM key, possibly $1,250 per year. Verdict: skip.

**obsidian-second-brain (eugeniughelbur, about 4.7k stars).** [source states] The only repo found with an explicit Grok Bot build: `bash scripts/build.sh --platform grok-bot` emits SKILL.md workflow files invoked with `/` or `@`, vault I/O goes through an MCP server with `obsidian_search`, `obsidian_read_note` and `obsidian_save_note`, and on Grok Bot there are "no scheduled agents or hook runtime"; its ingest command means "The vault REWRITES itself. 5-15 pages touched per source" ([GitHub](https://github.com/eugeniughelbur/obsidian-second-brain)). [inferred] What it adds: nothing the vault wants. Autonomous multi-page rewrites are the opposite of a read-only clone and Lane 4 gating, and its writes would be destroyed by the next `git pull` anyway. Cost: an MCP server plus 45 commands of skill surface. Verdict: skip; it is the clearest example of a repo built for someone who has no vault yet.

**second-brain-mcp (noesskeetit) and similar read-only vault servers.** [source states] Four read-only tools (`obsidian_overview`, `obsidian_search`, `obsidian_read`, `obsidian_backlinks`), "No auto-writes," local bge-m3 embeddings at about 2.3 GB on first run, 6 stars, v1.0.0 April 2026 ([GitHub](https://github.com/noesskeetit/second-brain-mcp)). Others in the same mould: [brain-mcp](https://github.com/dck/brain-mcp), [open-second-brain](https://github.com/itechmeat/open-second-brain). [inferred] The read-only design is correct for this fleet, but the only thing it adds over `grep` plus `INDEX.md` is semantic search, and a 2.3 GB model outside `/workspace` re-downloads after every update. Verdict: skip in favour of qmd below if semantic search is ever needed.

**qmd (Tobi Lütke), the search tool Karpathy names.** [source states] Installed via `npm install -g @tobilu/qmd`, offers BM25, vector and hybrid search with LLM reranking, auto-downloads three GGUF models (about 300 MB, 640 MB and 1.1 GB) to `~/.cache/qmd/models/`, stores its index at `~/.cache/qmd/index.sqlite`, and runs a stdio MCP server with five tools (`query`, `get`, `multi_get`, `status`, `metadata`) ([GitHub](https://github.com/tobi/qmd)). Runs on Grok Bot: yes, as a CLI from the terminal [inferred], provided `npm` installs to a `/workspace` prefix and the cache is redirected under `/workspace` — otherwise about 2 GB re-downloads after each update. [inferred] What it adds: ranked keyword search across the vault without opening files, which beats `grep -rn` when a Bot does not know the exact term (say, a facility referred to by unit name). The vault is 466 tracked notes and about 4.3 MB of markdown (measured locally 2026-10-04), with an `INDEX.md` of 28 KB, which is still "small scale" in Karpathy's sense. Cost: run as a CLI it is zero per turn; as an MCP server it is five schemas on every Bot's every turn. Verdict: try later, BM25 mode only and CLI only, and only if Bots are observed missing vault content that `grep` and `INDEX.md` should have found.

**Cline memory bank (pattern).** [source states] Six files — `projectbrief.md`, `productContext.md`, `activeContext.md` ("updates most frequently"), `systemPatterns.md`, `techContext.md`, `progress.md` — with the rule "I MUST read ALL memory bank files at the start of EVERY task" and an explicit "update memory bank" command that triggers a full review ([Cline docs](https://docs.cline.bot/prompting/cline-memory-bank)). Runs on Grok Bot: yes, plain files. [inferred] What it adds: `state.md` already covers `activeContext` and `progress` per job, and the vault covers the rest. Two things are worth taking: the explicit "update" verb that forces a full rewrite before context is lost, and the idea of a small per-agent file read at the start of every task. [inferred] The six-file split is too many for 15 Bots; one file per Bot is enough. Verdict: take the two ideas, skip the layout.

**memory-bank-mcp (gcorroto), MemPalace, Hindsight and the rest of the long tail.** [source states] memory-bank-mcp indexes codebases with vector embeddings ([GitHub](https://github.com/gcorroto/memory-bank-mcp)); MemPalace claims about 170 tokens of startup overhead and 96.6% on a retrieval-only LongMemEval metric ([unblocked comparison](https://getunblocked.com/blog/memory-mcp-servers-compared/)). [inferred] All are aimed at coding agents or chat recall and none addresses the actual failure here. Verdict: skip.

**Grok Bot's own server-synced memory (not shipped).** [source states] RuntimeWire found `ListGrokBotMemoryShards` and `PutGrokBotMemoryShard` in version 0.39.0 (2026-09-04), storing per-Bot "a `profile` string and a keyed `logs` map" apart from machine backups, but "no confirmed desktop call site," and it is unknown whether users can inspect memory before it is used ([RuntimeWire](https://runtimewire.com/article/grok-bot-is-building-server-synced-memory-for-its-ai-coworkers)). [source states] Cursor staff on 2026-09-23: "First class controls like same Bot new session with auto archiving the old thread... aren't shipped yet" ([forum 168333](https://forum.cursor.com/t/grok-bot-prune-compact-an-agent-s-context-without-creating-a-new-bot/168333)). [inferred] Either change would alter the reset routine below, so it is worth checking release notes monthly rather than building around its absence.

One source conflict to note: the Daily Dose of DS masterclass says the Bot "does not replay every prior message" ([dailydoseofds](https://www.dailydoseofds.com/p/grok-bot-masterclass/)), while Cursor staff say three times between 2026-09-01 and 2026-09-05 that "The full transcript is sent to the model on every turn" ([forum 168333](https://forum.cursor.com/t/grok-bot-prune-compact-an-agent-s-context-without-creating-a-new-bot/168333)). Staff win.

## What the fleet actually lacks

[inferred] The fleet has good homes for domain truth (vault), task state (`state.md`), methods (skills) and fleet rules (README). It has no home for a single Bot's own accumulated working knowledge — the corrections Jesse gave it, the quirks of a site it logs into, the file paths it keeps reusing, which outputs he rejected and why. Today that lives in the thread and in Grok's learned memory, and both are lost on a Duplicate reset ([source states] "Memory does not carry over," forum 171540, cited in the prior note). That is the one gap, and every repo above either ignores it or solves it with an opaque store.

The fix is a per-Bot file, `/workspace/bots/<BotName>/memory.md`, written only by that Bot, capped at about 150 lines, read at the start of every task, holding standing corrections, recurring paths and site quirks — never domain values, which go to the vault via Jesse. [inferred] At roughly 1.5K tokens it costs less per turn than a single MCP server's schemas, survives updates because it is under `/workspace`, is readable and editable by Jesse, and makes Duplicate lossless. It also follows the existing one-writer rule.

## Ranked recommendation

1. **Adopt: per-Bot `memory.md`** at `/workspace/bots/<BotName>/memory.md`, one writer, size-capped, added to `README-FOR-BOTS.md` under "memory lives in files". Lowest cost, closes the only real gap.
2. **Adopt: the reset routine below**, including the "update memory" verb borrowed from Cline. This is where the usage saving actually comes from.
3. **Already adopted: Karpathy LLM wiki.** No action; the vault is it.
4. **Try later, conditionally: qmd** as a BM25-only CLI under `/workspace`, never as an MCP, and only after observing Bots miss vault content.
5. **Watch: native Grok Bot memory shards and new-session control.** Re-check release notes monthly.
6. **Skip:** basic-memory, mem0/OpenMemory, Letta, Zep/Graphiti, obsidian-second-brain, second-brain-mcp, memory-bank-mcp and the long tail. Each either duplicates the vault, writes where Bots must not write, needs a database or API key that will not survive a computer update, or adds per-turn tool schemas across 15 Bots for a capability `grep` already provides.

## Thread-reset routine

**When to reset.** [inferred] Reset a Bot when any of these is true: its usage rows are past roughly 120K tokens per turn (the prior note's threshold, and README-FOR-BOTS warns calls cost double above 200K); it has just finished a job or bid and the next task is unrelated; it starts re-asking things already answered or contradicting `state.md`, which is the sign auto-summarization has dropped detail. Do not reset mid-task with an open deliverable — finish or park it in `state.md` first.

**Which reset.** [source states] Cursor staff on 2026-09-23 call a new group chat with the same Bot "the closest way to get a thin working set," because "the old 1:1 transcript isn't pulled into the working set" ([forum 168333](https://forum.cursor.com/t/grok-bot-prune-compact-an-agent-s-context-without-creating-a-new-bot/168333)). [inferred] Prefer the single-Bot group chat, since it is the same Bot and so should keep learned memory; use Duplicate when the Bot's profile or skills are also being changed, or when the group thread itself has grown long.

**What the handoff must contain.** The Bot writes it to a file, not into chat — partly for durability, partly because inter-Bot messages truncate silently at 8000 characters (README-FOR-BOTS):

- Every open job or bid it touches, each as a path to its `state.md`, confirmed up to date before the handoff is written.
- Its in-flight task: what was asked, what is done, the next concrete step, and the output path.
- Corrections Jesse gave it this thread that are not yet in a skill, the README or the vault — moved into `memory.md`.
- Any domain value it learned that belongs in the vault, listed as a flag for Jesse (Lane 4), not stored as fact.
- Files it created under `/workspace` that another Bot or Jesse needs, by path.
- Open questions it was waiting on, and from whom.

**Sequence.**

`Say "update memory" > Bot updates every state.md it owns and its memory.md > Bot writes /workspace/bots/<Bot>/handoff-YYYY-MM-DD.md > verify (below) > new group chat with the Bot alone (or right-click > Duplicate) > first message: "Read README-FOR-BOTS, your memory.md, and handoff-YYYY-MM-DD.md, then tell me your open work" > compare > hide or leave the old thread`

**How to verify nothing was lost.** [inferred] The check is a read-back by the fresh thread, not the old thread's self-report — an agreeing summary from the same thread proves nothing. Ask the new thread three things: list every open item with its next owner; name two corrections it is operating under; and answer one specific question whose answer was only in the old thread (pick it before resetting). Compare its open-item list against the `state.md` files directly. Anything missing goes back into `memory.md` or the relevant `state.md` before the old thread is hidden. Keep the handoff file; it is the record if something surfaces later.

## Open items

[inferred] Three things to check in the live app before relying on the routine: whether a single-Bot group chat really keeps that Bot's learned memory; whether a group chat's own thread shows the same per-turn growth (watch its usage rows for a few days); and whether `/workspace/bots/` should be created by one Bot with a README line naming the one-writer rule, or by Jesse directly.
